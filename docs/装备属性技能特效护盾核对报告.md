### 🔴 P0-1：`max_stacks` 是未实现的死字段

全项目 grep `max_stacks` 的命中：**仅** `UpgradeData.gd:40` 的定义 + 25 个 `.tres` 的赋值 + 3 处文档提及，**没有任何一行代码读取它**。

而三处声明都把它当作生效规则：
- `UpgradeData.gd:39` 注释：「全局统一规则：所有技能均可升至 **5 级**，满级后不再参与装备抽词」
- 《技能特效装备清单.md》第 12 行：「特效叠层**最高 5 级**」
- 《子弹弹道构型方案.md》:791：「技能 / 属性：同类叠层升级（有 `stacks` / `max_stacks` / 稀有度）」

实际叠层路径**全部无上限检查**：
- `BulletEffect.gd:44-47` `add_stack()` → 直接 `stack_count += 1`
- `Player.gd:409-419` `_stack_owned_effect()` → 直接 `owned.add_stack()`
- `UpgradeManager.gd:382-390` `boost_random_equipment_effect()` → 直接 `add_stack()`

**后果**：特效可无限叠层。配合神庙「强化装备特效」（碎片消耗 400 起步、每次 +100 累加），理论上可把单个特效堆到任意层级 —— 例如 `upg_lifesteal` 每级 +1 点固定回血、`upg_armorbreak` 每级 +4 点无视护盾核心伤害，无限叠层会直接破坏数值平衡。文档承诺的「满级后不再参与装备抽词」也未实现（抽词池从不检查层数）。

### ⚠️ 护盾系统发现

**B1.（P1）`regen_delay` / `regen_rate` 是死配置**
4 份 `.tres` 都写了 `regen_delay = 10.0`、`regen_rate = 7~10`，但实现完全用硬编码常量：
- `EquipmentShieldComponent.gd:57` `const BASE_REGEN_DELAY: float = 5.0`
- `EquipmentShieldComponent.gd:61` `const BASE_REGEN_DURATION: float = 5.0`
- `:56` 注释自陈：「旧值 `ShieldEquipmentData.regen_delay=10秒` 太慢，改为固定 5 秒」
- `:60` 注释自陈：「旧逻辑用固定 `regen_rate`……改为按比例回满」

grep 全项目，`regen_rate` 仅出现在字段定义与注释中，**无任何消费点**。→ 在编辑器里改这两项数值**不会影响游戏**，是典型的"数据驱动外壳 + 硬编码内核"。

**B2.（P0）玩家实际有两层护盾，无任何文档完整描述**
`Player.tscn` 同时挂载了两套护盾组件：

| 组件 | 节点路径 | 机制 | 实际数值 |
|---|---|---|---|
| `EquipmentShieldComponent` | `Player/EquipmentShieldComponent` | 耐久制 | 20~30 × 层数 × `shield_max_mult` |
| `ShieldComponent` | `Player/HealthController/ShieldComponent` | **分段制** | **3 段 × 10 = 30 点** |

伤害结算顺序（`Player.gd:657-682`）：
`减伤打折(damage_reduction)` → `装备护盾 absorb_damage()` → `health_controller.apply_damage()`（内部：分段护盾 `take_damage()` → 核心血）

分段护盾**默认就有 3 段 30 点**（`ShieldComponent.gd:61-65` 在 `shield_data == null` 时 `new()` 出默认值，`max_segments=3` / `segment_hp=10`）。

文档割裂：
- 《血条机制说明.md》**只**讲分段护盾 + 核心血，完全未提装备护盾
- 《技能特效装备清单.md》4.1 **只**讲装备护盾叠层，完全未提分段护盾

→ 玩家真实生存池 = 装备护盾 + 分段护盾(30) + 核心血(100+)，**没有任何一份文档描述过这个完整事实**。

### 🔴 P0-2：玩家开局自带「裂变之种」分裂特效

`player_default_bullet.tres` 的 `effects = [ExtResource("3")]`，而 `ExtResource("3")` 指向 `res://data/bullet/effect/split_effect.tres`。

`Player.gd:326-327` `_init_private_bullet_data()` 对该 `.tres` 做 `duplicate(true)` 深拷贝作为私有子弹副本 → **玩家从第一发子弹起就附带「子弹销毁时分裂 3 枚 60% 伤害小子弹」效果**。

而 `upg_split`（裂变之种）本应是需通过装备词条获取的 16 个特效之一。这造成：
1. 该特效白送，削弱装备掉落的获取感（与文档「杀戮即构筑」的设计哲学冲突）
2. 玩家再抽到 `upg_split` 时走 `Player.gd:445-446` 的叠层分支，直接变成 Lv2 起步
3. 无任何文档记录玩家初始自带分裂

需确认这是刻意设计（开局给一点弹幕爽感）还是配置残留。

### 🔴 P0-3：猎人的「追踪弹」普攻实际不追踪

`hunter_data.tres` 的 `bullet_data = enemy_homing_bullet.tres`，但该子弹文件**没有 `effects` 字段**（对比其余 8 份敌人子弹都有）：

```
enemy_homing_bullet.tres:  damage=4, speed=240, form=homing_bullet_form  ← 无 effects
```

`BulletForm` 只描述碰撞半径/颜色/尺寸（`homing_bullet_form.tres`：radius 7、紫色、14×14），**不含任何追踪逻辑**；追踪能力由 `HomingEffect`（`trigger_type = 3` ON_TRAVEL，每帧转向）提供。

→ 虚空猎人的普攻弹只是**外观紫色的直线弹**，不会追踪。它的追踪能力仅存在于 `skill_type = 4 HOMING_SHOT` 的技能弹（`hunter_homing`，追踪 3.5s）中。若设计意图是"猎人普攻即追踪"，则缺一个 `effects = [homing_effect]`。
